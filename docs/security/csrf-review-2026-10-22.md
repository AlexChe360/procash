# Проверка Cross-Site Request Forgery — 22 октября 2026

## Найденный дефект

Подтверждён обход CSRF через `HEAD`. В `net/http.ServeMux` маршрут `GET` также обслуживает `HEAD`. Часть обработчиков считала чтением только точный `GET`, а остальные методы направляла в логику изменения данных. При этом общая CSRF-проверка выполнялась только для `POST`.

На изолированном стенде регрессия `TestHEADCannotChangeProfileWithoutCSRF` до исправления действительно меняла имя пользователя через `HEAD` с query-параметрами, действующей session cookie и без CSRF-токена. Это требует отправки cookie жертвы: например, запрос из чужого, но same-site origin может включать `SameSite=Lax` cookies. Для обычного внешнего сайта отправка cookies дополнительно ограничена SameSite; это не делает изменяющий `HEAD` безопасным.

По исходному коду тот же неверный выбор ветки присутствовал во входе, публичной заявке, профиле, форме пароля и обеих анкетах. Требование текущего пароля при смене email/пароля отдельно сохранялось. Административные действия и платежи, зарегистрированные только как `POST`, уже проверяли CSRF.

## Исправления

- `GET` и `HEAD` явно обслуживают только чтение. Они не создают пользователей, сессии, заявки, письма, черновики или счётчики попыток входа и не меняют данные.
- Создание черновиков Freedom Pay и iiko перенесено из просмотра в транзакцию сохранения через защищённый `POST`. Незаполненная анкета отображается без записи в БД; отправка несохранённой анкеты возвращает ошибку валидации.
- Общая CSRF-проверка применяется ко всем unsafe-методам, включая `PUT`, `PATCH` и `DELETE`, а не только `POST`. Методические override-параметры/заголовки её не отключают. Неподдерживаемые маршруты по-прежнему не предоставляют этих операций.
- Подписанный double-submit токен привязан к конкретной session cookie. Вход и смена пароля меняют session и CSRF cookies вместе; выход и завершение доступа очищают обе. Токены других сеансов и старые анонимные токены не подходят для авторизованного сеанса.
- Токен принимается из `_csrf` в теле формы либо `X-CSRF-Token`. Query-параметр `_csrf` не используется. Дубликаты и противоречащие друг другу значения, а также неоднозначные cookies отклоняются. Все параметры изменения данных читаются из тела, а не URL.
- `Origin` сверяется с настроенным `APP_URL`, с учётом схемы, имени хоста и эффективного порта. Запрещены `null`, чужие/соседние origins, userinfo, пути и несколько значений Origin. При отсутствии Origin проверяется Referer. Proxy-заголовки не заменяют доверенный `APP_URL`.
- `Sec-Fetch-Site: cross-site` и `same-site` не считаются доверенными для изменения данных. При отсутствии Fetch Metadata/Origin/Referer сохраняется поддержка клиентов с корректной привязанной парой cookie/token; отсутствие заголовков само по себе не даёт доступ.
- Поддерживаются обычные HTML-формы, multipart и HTMX. Разбор тела ограничен 64 КиБ; ошибочный multipart не исполняет действие. Для устаревшей HTMX-формы показывается сообщение с просьбой обновить страницу.

В production сохраняются `Secure`, `HttpOnly`, `SameSite=Lax`, `Path=/`, отсутствие Domain и префикс `__Host-` у cookies. CORS-доступ внешним origins не добавлялся.

## Проверки

`internal/app/csrf_test.go` содержит матрицу **27 способов подделки × 37 POST-путей = 999 запросов**. Покрытие включает вход/выход, публичную заявку, аккаунт, смену пароля, заведения и столы, все шаги Freedom Pay, iiko, заявки и пользователей администратора, решения по интеграциям, повтор письма, удаление пользователя/заведения и mock-платежи.

Проверяются отсутствие/подмена токена и cookie, неверная подпись, перенос между сеансами, токен только в URL, дубликаты, конфликт заголовка и тела, чужой/`null`/неправильный Origin, Referer fallback, Fetch Metadata, proxy headers, `text/plain`, JSON, method override и попытка обхода через HX-заголовки. Каждый отклонённый запрос проверяется сравнением состояния всех таблиц приложения: пользователи, сессии, заведения, счета, платежи, анкеты, заявки, письма, аудит и rate limits. Появление нового POST-маршрута без покрытия матрицей приводит к ошибке теста.

Дополнительно проверяются безопасные `GET`/`HEAD`, остальные unsafe-методы, body-only данные, размер/формат multipart, корректная работа multipart и header-only запросов, нормализация origin, cookie flags, обновление токенов на границах входа/смены пароля/выхода.

`tests/csrf_browser.cjs` запускается в настоящем Chromium через локальные HTTPS-серверы с зарезервированными доменами `app.procash.test`, `evil.procash.test` и `attacker.other.test`. Он проверяет поддельные формы как из same-site sibling origin, так и из cross-site origin, настоящий credentialed `HEAD`, production-атрибуты cookies, ошибку устаревшего токена HTMX и успешное обычное изменение профиля. Серверная фиксация метаданных содержит только origin, путь и признак наличия session cookie, без значений cookies; эти тестовые HTTP-инструменты отсутствуют в production-приложении.

## Границы и обновление

Все атакующие запросы направлены в локальный стенд с отдельной временной схемой PostgreSQL. Настоящие письма не отправляются. Сертификаты тестовых HTTPS-серверов самоподписанные; их исключение действует только в тестовом браузере. Проверка внешнего production reverse proxy в этот аудит не входит; выпуск проверяет образ, страницу входа и соединение приложения с БД на сервере.

Формат подписи CSRF изменён. После установки этой версии уже открытые страницы необходимо обновить, прежде чем отправлять формы. Существующие аккаунты, пароли и данные сохраняются; общий сброс сеансов не выполняется.

Повторный запуск:

```bash
npm ci
npx playwright-core install --with-deps chromium
TEST_DATABASE_URL='postgres://.../procash_test?sslmode=disable' go test -race -count=1 ./...
```

Браузерные CSRF- и XSS-проверки входят в общий набор Go-тестов и обязательный GitHub Actions workflow.
