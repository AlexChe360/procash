# ProCash

Сервис подключения ресторанов и QR-счетов на **Go 1.27.3, PostgreSQL 17, HTMX 2 и TailwindCSS 4**. Сервер использует `net/http`, `html/template` и `pgx`; JavaScript и CSS поставляются локально, без runtime CDN. Готовый бинарник содержит шаблоны и frontend-ресурсы.

## Как работает подключение

1. «Подключить ресторан» открывает `/connect`. Контакты, заведение, город, касса и комментарий сохраняются в PostgreSQL. Аккаунт при этом не создаётся. `/register` перенаправляет на заявку, самостоятельный POST регистрации отключён.
2. Уведомление с ссылкой на заявку отправляется на **info@procash.kz**. Администратор видит все заявки в `/admin/requests`, может взять заявку в работу, отклонить с комментарием или выдать доступ.
3. Одобрение одной транзакцией создаёт пользователя и заведение, связывает их с заявкой и ставит письмо с доступом в очередь. Повторное одобрение не создаёт дубликаты. Для существующего пользователя создаётся дополнительное заведение; по умолчанию пароль сохраняется. Если доступ ему ещё не выдавался или пароль неизвестен, администратор может явно выбрать выдачу нового временного пароля при одобрении. В обработанной заявке также есть кнопка выдачи нового пароля; это завершает прежние сессии и отправляет новый доступ на email пользователя.
4. Новый пользователь получает ссылку `/login` и случайный временный пароль на 7 дней. Пароль один раз показывается администратору; в базе пользователя хранится только bcrypt. При первом входе обязательно установить собственный пароль.
5. В `/account` пользователь меняет имя, телефон и email. Изменение email требует текущего пароля и завершает сессии. Пароль меняется отдельно; другие сессии отзываются. Администратор может отключить клиента или выдать новый временный пароль.

Публичная главная сохраняет прежний дизайн. Кабинет и админ-панель адаптированы для телефона и компьютера. Навигация, фильтры и формы используют HTMX; основные действия работают и обычными HTML-формами.

## Заведения, метрики и подключения

- Владелец видит только свои заведения; администратор — все. Можно менять контакты заведения, создавать столы и скачивать настоящие PNG QR-коды. Прежние публичные URL `/r/{slug}/q/{token}` сохраняются вместе с UUID и QR-токенами.
- Обзор показывает число заведений, активных заведений, столов, заказов, оплаченных счетов и оборот за 7/30/90 дней. Есть разбивка по заведению. Дни считаются в `Asia/Almaty`, суммы агрегируются PostgreSQL `numeric`, чужие данные исключены.
- **Freedom Pay:** прежняя пятишаговая анкета, проверка, отправка на рассмотрение ProCash, исправления по комментарию, сопровождение администратором и подтверждение подключения с реальным merchant ID.
- **iiko:** контактные данные, адрес, вариант и версия кассы, необязательный адрес сервера и комментарий; сохранение черновика, отправка, обработка, исправления и подтверждение подключения.
- Отправка анкет уведомляет ProCash по почте; решения администратора уведомляют владельца. Работа с API Freedom Pay и iiko, получение новых POS-счетов и реальный эквайринг требуют отдельной настройки интеграций с партнёрами. Смена статуса не имитирует отправку в их API и не создаёт фиктивные merchant ID.
- Существующие заказы и платежи доступны. Публичный QR показывает сохранённый открытый счёт. Mock-оплата явно помечена как тестовая и отключена в production по умолчанию.

## Почта и состояние

Redis сейчас не требуется: сессии, ограничение попыток и очередь писем хранятся в PostgreSQL. Они переживают перезапуск и не зависят от конкретного экземпляра приложения. Для текущих метрик достаточно SQL-индексов; отдельного слоя кэша нет.

Письма создаются в той же транзакции, что и заявка/выдача доступа. SMTP worker использует `FOR UPDATE SKIP LOCKED`, lease и повторные попытки с задержкой. После 24 неудач письмо доступно для ручного повтора в `/admin/mail`. Доставка имеет семантику at least once; постоянный Message-ID помогает распознавать повтор. Статус «Доставлено SMTP-серверу» означает принятие сервером, а не гарантированное прочтение получателем.

Тела ожидающих писем зашифрованы AES-GCM постоянным `APP_KEY`; после успешной отправки тело удаляется. Временные пароли не попадают в логи или постоянный интерфейс. `APP_KEY` нельзя менять при обычном деплое.

Поддерживаются `SMTP_HOST`, `SMTP_PORT`, `SMTP_USERNAME`, `SMTP_PASSWORD`, `SMTP_FROM`, `SMTP_SECURITY` (`starttls` по умолчанию, `tls` для implicit TLS). Прежние `MAIL_HOST`, `MAIL_PORT`, `MAIL_USERNAME`, `MAIL_PASSWORD`, `MAIL_FROM_ADDRESS` также поддерживаются. Для порта 465 без явного `SMTP_SECURITY` автоматически выбирается `tls`. В production TLS обязателен, проверка сертификата включена. `NOTIFY_EMAIL` по умолчанию — `info@procash.kz`.

## Разработка

Нужны Go 1.27.3+, Node.js 24 с npm и PostgreSQL 17. Node нужен для сборки ресурсов, а не для работы сервера.

```bash
cp .env.example .env
# Настройте DB_* для локальной PostgreSQL.
./bin/setup
.deploy/bin/procash serve
```

`bin/setup` устанавливает зависимости по lock-файлам, проверяет Go-модули, собирает Tailwind и бинарник, создаёт ключ только при отсутствии и запускает обычные миграции. `bin/go` использует Go из облачной среды, если он установлен там; на обычной машине — системный Go.

После изменений шаблонов и CSS пересоберите ресурсы и бинарник:

```bash
npm run build
go build -o .deploy/bin/procash ./cmd/procash
.deploy/bin/procash serve
```

Администратор создаётся или обновляется серверной CLI-командой; пароль вводится скрыто, не передаётся аргументом:

```bash
.deploy/bin/procash admin --email admin@example.com
# На сервере:
docker compose exec app procash admin --email admin@example.com
```

Прежние администраторы и пароли Laravel/Spring сохраняются. Нового встроенного аккаунта или общего пароля нет.

Если SSH с компьютера недоступен, используйте GitHub Actions → **Manage ProCash administrator** → **Run workflow** на ветке `main`:

1. Добавьте repository secret `ADMIN_BOOTSTRAP_PASSWORD` с новым паролем (12–72 байта UTF-8, без переводов строк).
2. В ручном запуске укажите email администратора; по умолчанию `info@procash.kz`.
3. После успешного запуска войдите на `https://procash.kz/login` с указанными email и паролем. Удалите временный secret из GitHub после использования.

Этот запуск создаёт администратора либо меняет пароль и роль указанного существующего аккаунта, включая отзыв его сессий. Он использует существующие `VPS_*` secrets, проверяет SSH host key и ждёт блокировку деплоя перед изменением аккаунта. Пароль передаётся по stdin и не выводится в лог. Запуск выполняется только вручную; обычный деплой пароль не меняет.

## Проверки

Проверка XSS описана в [отчёте](docs/security/xss-review-2026-10-22.md). Перед интеграционными Go-тестами установите Chromium командой `npx playwright-core install --with-deps chromium` либо задайте `CHROMIUM_PATH` к системному браузеру. Тесты включают браузерные регрессии для экранирования, CSP и HTMX. Override `@parcel/watcher` до 2.6.0 устраняет уязвимую цепочку `micromatch`/`braces`, закреплённую в Tailwind CLI.

Используйте отдельную тестовую PostgreSQL, в имени которой есть `test`. Каждый интеграционный тест создаёт и удаляет только собственную схему внутри этой базы. Рабочие таблицы не очищаются.

```bash
export TEST_DATABASE_URL='postgres://procash_user:password@127.0.0.1:5432/procash_test?sslmode=disable'
npm ci
npm run build
go mod verify
go vet ./...
go test -race -count=1 ./...
go build -o /tmp/procash ./cmd/procash
PROCASH_TEST_BINARY=/tmp/procash python3 tests/deploy_workflow_test.py
```

Без `TEST_DATABASE_URL` интеграционные тесты явно пропускаются; это не подтверждает готовность. CI всегда предоставляет PostgreSQL и выполняет их. Проверяются запрет самостоятельной регистрации, выдача доступа, первый вход, отзыв сессий, старые bcrypt-хеши, CSRF, права владельца/администратора, обе анкеты, метрики, QR, повторная mock-оплата, очередь писем и обработка ошибок.

Python-тесты сценария деплоя используют настоящий Git и Go helper с управляемыми подменами Docker/HTTP: проверяют повторный запуск, сохранение ключей, резервную копию, недоступную почтовую конфигурацию, ошибки миграции/health, откат образа и сохранение локальных изменений.

## Production и миграция

```bash
docker build --target production -t procash:local .
# Настройте серверный .env: APP_KEY, APP_URL=https://procash.kz,
# POSTGRES_DB, POSTGRES_USER, POSTGRES_PASSWORD и SMTP_* / MAIL_*.
docker compose config --quiet
docker compose up -d --wait db
docker compose run --rm app check-config
docker compose run --rm app migrate
docker compose up -d --wait app
```

Готовый образ содержит статический Go-бинарник и доверенные CA-сертификаты; работает под UID/GID 10001 без PHP, Node и shell. Порт `8080` привязан к `127.0.0.1`. HTTPS завершается прежним внешним reverse proxy; HTTP должен перенаправляться на HTTPS. Формы и ссылки интерфейса относительные, QR и письма используют проверенный `APP_URL`. Cookie сессии в production имеет `Secure`, `HttpOnly`, `SameSite=Lax` и префикс `__Host-`. Переданный IP клиента учитывается только от внутреннего/loopback reverse proxy; прокси должен перезаписывать или дополнять `X-Forwarded-For` фактическим IP.

Миграции в `internal/db/migrations` транзакционные, версионируются в `go_schema_migrations` и защищены advisory lock. Принимают прежние таблицы, добавляют нужные поля и новые таблицы. UUID, пользователи, bcrypt-хеши, заведения, QR-токены, заявки Freedom Pay, счета, платежи и история прежних миграций не заменяются. Старые файловые сессии не переносятся: потребуется войти заново. Отката с удалением таблиц нет.

**Сохраняйте прежнее имя Compose project и том `procash_postgres_data`.** Том файловых сессий Laravel больше не нужен приложению, но скрипт его не удаляет: он остаётся доступен при откате старого образа.

`/actuator/health`, `/api/v1/health`, `/up` действительно проверяют соединение с БД. `procash check-config` проверяет обязательные production-параметры, включая наличие SMTP; он не отправляет тестовое письмо и не подтверждает доставку в почтовый ящик.

## GitHub Actions

Push в `main` запускает **Deploy ProCash**:

1. Проверка lock-файлов и ресурсов, `go vet`, форматирование, тесты с PostgreSQL и race detector, тесты деплоя.
2. Сборка production-образа, публикация в GHCR с SHA и OCI revision, получение digest.
3. SSH-деплой конкретного digest, сверка revision, проверка конфигурации почты, `pg_dump` и проверка архива, миграции, запуск, SQL health и страница входа.

При ошибке до замены app старое приложение продолжает работать. При ошибке нового app восстанавливаются прежние checkout и image ID. База автоматически не откатывается; проверенная копия находится в `.deploy/backups/`. Деплои не прерывают друг друга и защищены серверным `flock`.

Используются прежние secrets `VPS_HOST`, `VPS_USER`, `VPS_SSH_KEY`, `VPS_KNOWN_HOSTS`; variables `VPS_PORT` (22), `VPS_DEPLOY_PATH` (`/opt/procash`). На сервере нужны Docker Compose v2.20+, Git, curl, flock и действующий доступ Git к origin. GHCR использует временный `GITHUB_TOKEN`, отдельный PAT не нужен.

SMTP берётся из существующего серверного `.env`. При наличии repository secrets `SMTP_HOST`, `SMTP_PORT`, `SMTP_USERNAME`, `SMTP_PASSWORD`, `SMTP_FROM`, `SMTP_SECURITY` Actions безопасно передаёт непустые значения через SSH stdin и атомарно обновляет `.env` без shell `source`. Пустые secrets не стирают серверные значения. Перед применением миграций отсутствие обязательной почтовой конфигурации останавливает деплой, оставляя прежний сервис.
